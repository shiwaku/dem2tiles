# 検証レポート: 低ズームのオーバービュー化と入力を開く回数の削減（2026-09-28）

#17（低ズームの RGB 系タイルが原寸のラスタを読んで極端に遅い）と #18（入力ファイルを
開く処理が 1 回の実行で何度も走る）の修正を確かめた。

## 変更の内容

| | 変更前 | 変更後 |
| --- | --- | --- |
| VRT | merge の中で作る | 最初の工程として一度だけ作り、キャッシュする |
| 入力の点検（`probe.py`） | 全ファイルを開いて座標系を集計 | VRT に入った図郭を入力の一覧と突き合わせ、抜けたものだけ開く |
| タイルの範囲（`tile_driver.py`） | 全ファイルを開く（RGB 系 1 種ごと） | VRT の `DstRect` から求める |
| 低ズームのタイル | 原寸のラスタから縮める | `merged_filled.tif.ovr`（`gdaladdo -r average`）の合う段から縮める |

入力ファイルを全部開くのは、初回の `gdalbuildvrt` の 1 回だけになる。入力が同じ再実行では
1 回も開かない。

## 結論

- 静岡（1164 図郭）で RGB 系タイルの生成が 601 秒から 143 秒になった
- 元の解像度に近いズーム（z16〜17）のタイルは、変更前とバイト単位で同じ
- z5〜15 は値が少し変わる。データの縁から離れた場所では 99.9% が 0.27 m 以内
- 数値PNG（gsidem）は変わらない
- タイルの枚数（範囲の計算）は変わらない

## 処理時間

タイムスタンプは gawk の `systime()` で付けた（1 行ずつ `date` を起動すると記録が遅れる。
[`verification-shizuoka.md`](verification-shizuoka.md) の訂正を参照）。

### 静岡（1164 図郭、入力は Windows のフォルダをマウント）

merge・fill・数値PNG は作成済みのものを使い、RGB 系タイルだけを作り直した。

| 工程 | 変更前 | 変更後 |
| --- | --- | --- |
| 入力の点検 | 10 秒 | 0 秒（VRT を再利用） |
| オーバービューの作成 | ― | 34 秒（初回のみ。今回は作成済み） |
| Terrain-RGB（範囲の計算を含む） | 303 秒 | 66 秒 |
| Terrarium（範囲の計算を含む） | 298 秒 | 77 秒 |
| 合計 | 626 秒 | 151 秒 |

範囲の計算は、変更前は RGB 系 1 種ごとに約 9 秒、変更後は 1 秒未満。

### 山梨の 400 図郭（08ME03/04/13/14、入力はローカルの一時フォルダ）

出力を空にして、最初から実行した。

| 工程 | 変更前 | 変更後 |
| --- | --- | --- |
| VRT の作成と入力の点検 | 2 秒 | 5 秒 |
| merge〜fill | 27 秒 | 22 秒 |
| オーバービューの作成 | ― | 4 秒 |
| Terrain-RGB | 40 秒 | 29 秒 |

範囲が狭い（17,073 x 10,491 px）うえ、入力を開く操作も速い環境なので、差は小さい。

山梨県全域では、#18 の 3 つの処理（計 1,659 秒）のうち、`probe.py` の 449 秒と

## 出力の変化

### ズームごとの一致（変更前と変更後）

| ズーム | 静岡 | 山梨 400 図郭 |
| --- | --- | --- |
| z16〜17 | 2,942 / 2,942 枚がバイト一致 | 1,046 / 1,046 枚がバイト一致 |
| z5〜15 | 値が変わる（下表） | 値が変わる（下表） |

どちらのデータも、Terrain-RGB と Terrarium で同じ結果だった。数値PNG は全ファイルが一致した。
同じ条件で 2 回実行した出力も、変更前・変更後ともバイト単位で一致した（処理は決定的）。

### z5〜15 の値の変化

| | 静岡（Terrarium） | 山梨 400 図郭（Terrarium） |
| --- | --- | --- |
| 変化量の平均 | 0.001〜0.002 m | 0.001〜0.46 m（ズームによる） |
| 変化量の p99 | 0.04 m 以下 | 0.42 m 以下 |
| 最大 | 4.2 m | 668 m |

山梨の最大値が大きいのは、データの縁で標高 1,000 m 級の地面と 0 で埋めた画素が接する
ため。山梨の 400 図郭で詳しく見ると:

- 5 m を超えて変わった画素の 97.6% は、0 で埋めた画素から 3 px 以内にある
- 縁から離れた場所では、中央値 0.008 m、p99 0.09 m、p99.9 0.27 m

縁の崖を、オーバービューで平均してから縮めるか、元の解像度から双線形で縮めるかの違い。
どちらも 0 埋めの影響を受けた値で、どちらが正しいというものではない。

## 再現手順

```bash
docker build -t dem2tiles .
docker run --rm -v /path/to/dem:/input:ro -v $(pwd)/output:/output dem2tiles \
  | awk -v s=$(date +%s) '{printf "%5ds  %s\n", systime()-s, $0; fflush()}' > run.log

# 変更前の出力と比べる。z5〜15 は値が変わるので "pixel diff" として報告され、
# RESULT は MISMATCH になる。z16〜17 と gsidem が一致することを確かめる
python scripts/verify_tiles.py --old output-before --new output --old-ext webp --new-ext webp
```
